# 手机比例布局适配 — 立项说明

给接手这项工作的 AI。这份文档只讲这一件事：**让编辑器在手机竖屏下可用**。

先读 `docs/ios-platform-notes.md`（尤其是 iOS 那节），再读这份。

## 目标

编辑器目前是按平板设计的，控件密度对手机屏幕来说过高。要做的是一层随屏幕形态
切换的布局，让手机上能正常用。

用户给的方向（设计意图，不是实现规格）：

- 控件太多、手机屏幕太小，顶部标签那样横排放不下
- 顶部导航在手机上应改成**从左侧展开**的形式
- 其余手机端该有的设计一并考虑

**iPhone 与 Android 共用同一套界面。** 这是用户的决定：iOS 真机测试成本太高，
所以本项工作只在 Android 上验证。共享编辑器源码本来就被三端同时编译，做对了
iPhone 自然跟着变。

## 第一硬约束：不能把平板布局搞没了

用户明确提的要求，而且**当前没有任何自动化回归防线**——`LumaChart.Avalonia.Specs`
里没有针对平板布局的断言，改坏了不会有任何东西报错。

保护分两层，**两层都要有**。

**第一层，结构性闸门（底线）：**

> 手机布局必须是**增量的、由断点闸门控制的**。在断点以上，代码走的路径应当与
> 今天**逐字相同**——不是"看起来一样"，是同一个分支。

这样即便手边没有平板可测，平板行为也不可能退化。任何"顺手把现有布局也重构一下"
的改动都违反这条，无论看起来多合理。推论：**不要为了手机去改现有的布局代码**，
新增手机分支，让旧路径原样保留。

**第二层，自动化断言（必须补上）：**

结构性闸门只保证"平板走的还是老代码"，它**证明不了老代码在平板尺寸下摆得对**，
也挡不住以后有人无意间把闸门条件改宽。用户明确要求这层要有。

在 `LumaChart.Avalonia.Specs` 里补布局断言，至少覆盖：

- 断点判定本身——给定 dp 宽高，选中的是手机还是平板布局。这是纯函数，最容易断言，
  也最该先写。**先把断点判定抽成不依赖控件树的可测函数**，再谈其余。
- 平板尺寸下，导航仍是顶部形态、检查器标签页仍在原位
- 手机尺寸下，没有任何控件的期望宽度超出可用宽度
- 两种形态下，编辑器可用的核心命令集合完全一致（布局可以变，操作逻辑不能丢）

这层断言要在**动布局代码之前**先写好平板那半边，否则它证明不了"没弄坏"——只能
证明"现在是这样"。

## 尺寸不要写死

用户明确提的。现在 `MainWindow.cs` 里散着 `430`(房间上传弹窗)、`330`(好友面板)
这样的字面量，它们正是手机上溢出的直接原因。新代码不要再产生这类常量：

- 尺寸从**可用空间推导**（占比、`MaxWidth` 绑定到容器、`*` 权重），不要从设备型号
  或某个具体分辨率反推
- 断点阈值等确实需要的常量，**集中到一处具名定义**，不要散落在构建代码里
- 已有的写死值，**只在它确实挡住手机布局时才改**，改的时候要落在断点分支内，
  不能动平板路径的取值（见上面第一硬约束）

## 已核实的现状

以下都是查过的事实，不是推测：

| 事实 | 含义 |
|---|---|
| 代码里**基本没有自适应/断点逻辑**（唯一命中的是 Android 清单的 `ConfigChanges` 标志，与布局无关） | 这一层是从零建，不是改造 |
| `LumaChart.iOS/Info.plist` 的 `UIDeviceFamily` 已声明 `1`(iPhone) 和 `2`(iPad) | 手机上现在就能装，只是拿到被挤压的平板布局。**纯布局问题，不涉及清单改动或商店重新提交** |
| 界面**全部是 C# 手写构建的**，仓库里一个 `.axaml` 都没有 | 没有 XAML 触发器或样式选择器可用，断点切换得在 C# 里显式做 |
| `MainWindow.cs` 是 **23,416 行 / 1 MB 单文件** | 本项工作最大的风险，见下 |
| `MainWindow.cs` 里有写死的像素宽度，如 `430`(房间上传弹窗)、`330`(好友面板) | 手机竖屏逻辑宽度约 360–410dp，**这些现在就是溢出的**。是现成的落地切入点 |

### 入口地址

- `LumaChart.Avalonia/MainWindow.cs:3846` — `BuildNavigation()`，顶部导航在这里构建
- `LumaChart.Avalonia/MainWindow.cs:401` — `editorInspectorTabs`（`TabControl`），检查器标签页
- `LumaChart.Avalonia/Controls/TimelineSurface.cs` — 时间轴/note 网格（179 KB）
- `LumaChart.Avalonia.Shared/AndroidApp.cs` — Android 的编辑器装配入口
- `LumaChart.Avalonia.Mobile/IOSApp.cs` — iOS 的对应入口

### 关于那个 1 MB 文件

23,416 行、界面全是命令式 C#。做布局改造要反复翻它，任何 AI 的上下文都会被它吃掉。

**建议先评估把外壳/导航部分抽出成独立文件再动手**，否则开局就陷在读文件里。但注意
这属于重构，与上面的第一硬约束有张力：抽取时必须保证行为逐字不变，且**单独成一个
提交**，不要和手机布局混在一起。

## 测试回路：只有 Android

用户会用 USB 插一台 Android 手机。**没有平板真机**，平板靠上面的结构性约束保护，
必要时用 Android 模拟器的平板配置过一眼。

工具链已核实存在，`adb.exe` 就在 scrcpy 目录里：

```
D:\Tool\scrcpy-win64-v3.3.3\adb.exe
D:\Tool\scrcpy-win64-v3.3.3\scrcpy-console.bat
```

分工要分清：

- **scrcpy 是给人看的**——用户自己开窗口盯屏幕
- **adb 是给 agent 用的**——截图自己看，不要指望 scrcpy

```powershell
$ADB = "D:\Tool\scrcpy-win64-v3.3.3\adb.exe"
& $ADB devices                                   # 先确认设备在
& $ADB shell wm size                             # 真实分辨率
& $ADB shell wm density                          # dpi，算逻辑宽度要用
& $ADB exec-out screencap -p > shot.png          # agent 自己看布局
& $ADB logcat -d -s DOTNET:* AndroidRuntime:*    # 崩溃和托管异常
```

构建安装：

```powershell
.\tools\Build-AndroidApk.ps1 -Configuration Release   # 需 LUMACHART_ANDROID_* 签名环境变量；自测包可加 -AllowDebugSigning
& $ADB install -r <apk 路径>
```

**逻辑宽度自己算**：`wm size` 给的是物理像素，除以 `wm density`/160 才是布局用的 dp。
断点要按 dp 定，不是按像素。

## 未决的设计问题（用户还没定，别自己定死）

- 左侧抽屉是**覆盖式**（浮在编辑区上方，收起后不占空间）还是**推挤式**（把编辑区
  推窄）？手机竖屏下 note 网格的横向像素是最稀缺的资源，这个选择影响很大。
- 断点定在多少 dp？以及是只看宽度，还是宽高比也参与判断（横屏手机的宽度可能超过
  竖屏平板）。
- 检查器标签页（`editorInspectorTabs`）在手机上怎么处理——同样收进抽屉，还是改成
  底部弹出？
- 时间轴在手机上的最小可用高度是多少，会不会需要一个"专注编辑"模式把周边控件全收掉。

遇到这些**先问用户**，不要替他决定。

## 工作纪律

本项工作尤其要注意两条：

- **平台条件分支的改动，Windows 规格套件通过不构成验证。** 手机布局走的是另一个
  分支，必须用 adb 截图亲眼看过。历史上有一次「只是删个按钮」跳过了这步，结果焦点
  顺序断号，iOS 启动即崩。
- **先拿证据再给结论。** 截图、`wm size` 的实际值，都比推理可靠。

发布前的老规矩不变：两个规格套件全绿、Windows 和 Android 的 Release 零警告。
